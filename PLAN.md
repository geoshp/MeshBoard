# MeshBoard — план работ

Веб-дашборд для companion-ноды MeshCore. Backend: Python 3.12 + asyncio + FastAPI + WebSocket + SQLite (WAL).
Frontend: Vite + React + TypeScript, ECharts, Leaflet. Запуск: docker compose.

Библиотека: `meshcore` (meshcore_py) **2.3.19** — изучены README, исходники (`meshcore.py`, `reader.py`,
`commands/*.py`, `parsing.py`, `meshcore_parser.py`, `connection_manager.py`, `*_cx.py`) и `examples/`.
Ниже используются только реально существующие методы и события этой версии.

## Этапы

1. **Каркас, docker, mock, подключение** — структура проекта, конфигурация из окружения, логирование
   с маскировкой секретов, авторизация, SQLite-схема, сервис подключения к ноде (serial/tcp) с
   автопереподключением, эмулятор ноды (`MESHCORE_MOCK=1`), WebSocket-хаб, статус соединения в UI,
   Dockerfile (multi-stage), docker-compose, `.env.example`.
2. **Каналы и ЛС** — список каналов, лента в реальном времени, отправка, SNR/RSSI/путь; контакты,
   диалоги, отправка с ack, счётчик непрочитанных.
3. **Репитеры и графики** — флаг «мой репитер», опрос по расписанию (статус, телеметрия, соседи),
   метрики своей ноды, графики с выбором периода.
4. **Карта и трассировки** — контакты/репитеры с GPS, цвет по давности, линии маршрутов
   (out_path контактов, пути из принятых сообщений, результаты trace, соседи репитеров), запуск trace.
5. **Тесты и README** — pytest (разбор событий, хранение, API, сквозной прогон на эмуляторе),
   README с запуском для USB, WiFi и mock, проверка на утечки секретов.

## Архитектура

```
backend/app/
  config.py        настройки из окружения (+ *_FILE для Docker secrets)
  logsetup.py      логирование, фильтр-маскировщик секретов, логгер meshcore не ниже INFO
  db.py            SQLite (WAL), схема, запросы, ретеншн
  parse.py         чистые функции: payload событий meshcore -> строки БД (тестируются отдельно)
  hub.py           рассылка live-событий по WebSocket
  node.py          NodeService: подключение, супервизор переподключения, подписки на события,
                   команды (отправка, trace), опрос метрик своей ноды
  repeaters.py     опрос своих репитеров по расписанию
  auth.py          пароль из окружения, подписанная cookie-сессия, лимит попыток
  api.py           REST + WebSocket
  main.py          фабрика приложения, lifespan, раздача собранного фронтенда
  mock/emulator.py эмулятор companion-ноды: TCP-сервер, говорящий бинарным протоколом MeshCore
frontend/          Vite + React + TS
```

**Эмулятор работает на уровне протокола**: в режиме mock backend поднимает внутри процесса
TCP-сервер на 127.0.0.1, который отвечает кадрами companion-протокола (SELF_INFO, CONTACT,
CHANNEL_INFO, *_MSG_RECV_V3, MSG_SENT, ACK, BINARY_RESPONSE, TRACE_DATA, LOG_DATA и т.д.), а backend
подключается к нему обычным `MeshCore.create_tcp(...)`. Поэтому в mock работает тот же код
подключения и разбора, что и с железом, а тесты проверяют реальный парсер библиотеки.

## Какие API библиотеки используются

| Задача | API meshcore 2.3.19 |
|---|---|
| Подключение | `MeshCore.create_serial(port, baudrate, auto_reconnect=True, ...)`, `MeshCore.create_tcp(host, port, ...)` |
| Статус соединения | события `CONNECTED` / `DISCONNECTED`, `mc.is_connected` |
| Инфо о ноде | `mc.self_info` (после appstart), `commands.send_device_query()` → `DEVICE_INFO` |
| Контакты | `commands.get_contacts()` → `CONTACTS`; `mc.contacts`; события `ADVERTISEMENT`, `PATH_UPDATE`, `NEW_CONTACT` |
| Каналы | `commands.get_channel(idx)` → `CHANNEL_INFO` (до `max_channels` из `DEVICE_INFO`) |
| Приём сообщений | `mc.start_auto_message_fetching()` + события `CONTACT_MSG_RECV`, `CHANNEL_MSG_RECV` |
| Путь/RSSI сообщений канала | `mc.set_decrypt_channel_logs(True)` + `RX_LOG_DATA`: библиотека сама сопоставляет лог с сообщением и добавляет `path`, `RSSI` |
| Отправка в канал | `commands.send_chan_msg(idx, text)` → `OK` |
| Отправка ЛС + ack | `commands.send_msg_with_retry(contact, text)` (повторы, ожидание `ACK`), `ACK.trip_time` |
| Логин в репитер | `commands.send_login_sync(contact, password)` → `LOGIN_SUCCESS` или `None` |
| Статус репитера | `commands.req_status_sync(contact)` → dict (`bat`, `uptime`, `airtime`, `nb_recv`, ...) |
| Телеметрия | `commands.req_telemetry_sync(contact)` → список LPP |
| Соседи | `commands.fetch_all_neighbours(contact)` → `neighbours[{pubkey(префикс), secs_ago, snr}]` |
| Метрики своей ноды | `get_bat()`, `get_stats_core()`, `get_stats_radio()`, `get_stats_packets()` |
| Trace | `commands.send_trace(path="aa,bb,...", tag=...)` + `wait_for_event(TRACE_DATA, {"tag": tag})` |

## Чего нет в библиотеке / ограничения (важно)

- **Нет истории сообщений на ноде.** Companion отдаёт только очередь непрочитанных (`get_msg`), после
  выборки сообщение из очереди удаляется. Вся история — только в нашей SQLite.
- **Отправитель сообщения канала** не передаётся отдельным полем: по соглашению прошивки он в тексте
  (`"Имя: текст"`). Разбираем префикс до первого `": "`.
- **SNR** приходит только в кадрах v3 (`CONTACT_MSG_RECV_V3`/`CHANNEL_MSG_RECV_V3`).
  **RSSI и путь (список хопов)** для сообщений каналов есть только через сопоставление с `RX_LOG_DATA`
  (`set_decrypt_channel_logs(True)` + загруженные `get_channel()`); требуется, чтобы прошивка слала
  `LOG_RX_DATA`. Если сопоставление не удалось — показываем только `path_len` (число хопов).
- **Для ЛС** библиотека отдаёт только `path_len` и SNR: RSSI и байты пути недоступны (ЛС зашифрованы
  ключом пары, библиотека их в логах не расшифровывает). Путь к контакту берём из `out_path` контакта.
- **Ack есть только у ЛС.** У сообщений каналов подтверждения нет (`send_chan_msg` возвращает лишь
  `OK` от самой ноды) — статус «отправлено ноде».
- **Счётчик непрочитанных** библиотека не ведёт — реализован в приложении.
- **Флага «свой репитер»** в протоколе нет — хранится в настройках приложения.
- **Пароль репитера** нужен для `send_login_sync`; библиотека ждёт только `LOGIN_SUCCESS` (на
  `LOGIN_FAILED` — ожидание до таймаута). Пароли берём только из окружения / Docker secrets.
- **Соседи репитера** приходят с префиксами ключей (по умолчанию 4 байта) — сопоставляем с контактами
  по префиксу, возможна неоднозначность.
- **Trace**: в ответе только хэши хопов (1/2/4 байта) и SNR, без ключей. Пакет trace пересылают только
  репитеры; маршрут строим «туда и обратно»: `out_path` контакта + хэш цели + обратный `out_path`.
  Если путь к контакту неизвестен (flood), trace идёт только до цели как до прямого соседа.
- **`get_bat()`**: поле называется `level`, но прошивка отдаёт напряжение в мВ — так и показываем.
- **`get_stats_*`** есть только в новых прошивках; на старых возвращается `ERROR` — графики airtime/
  пакетов своей ноды тогда пустые (у репитеров эти данные есть в `req_status_sync`).
- **Автопереподключение библиотеки** ограничено `max_reconnect_attempts` с паузой 1 с; поверх него
  сделан собственный супервизор с экспоненциальной паузой и бесконечными попытками.
- **Замечание о библиотеке**: `commands.reset_path()` в 2.3.19 отправляет код 0x3B
  (`GET_AUTOADD_CONFIG`), а не `RESET_PATH`, поэтому flood-фолбэк в `send_msg_with_retry` фактически
  не сбрасывает путь на ноде. Мы `reset_path` напрямую не используем.
- **Безопасность логов**: при `debug=True` библиотека пишет в лог сырые байты кадров (включая пароль
  логина в репитер). Поэтому логгер `meshcore` принудительно не ниже INFO, а `debug` не включается.
- **Выборка сообщений**: вместо `start_auto_message_fetching()` используется собственный цикл
  `commands.get_msg()` по событию `MESSAGES_WAITING` под общей блокировкой команд — библиотека
  сопоставляет ответы по типу события, и параллельные команды могли бы перехватить чужой `ERROR`.
- **Повторы ЛС**: логика как в `send_msg_with_retry` (тот же timestamp, `attempt=0..2`, ACK на любую
  попытку = доставлено), но блокировка держится только на время `send_msg`, ACK ждём вне её.
- **Лимит длины**: прошивка ограничивает текст 160 байтами; для каналов из лимита вычитается
  `"Имя: "`, который добавляет нода. В UI считается длина в байтах UTF-8.
- **Опрос репитеров**: те же шаги, что в `req_status_sync`/`req_telemetry_sync`/`fetch_all_neighbours`
  (`send_binary_req` + ожидание ответа по `tag`), но без удержания блокировки на время ожидания ответа
  по радио. Для логина используется `send_login` + ожидание `LOGIN_SUCCESS`/`LOGIN_FAILED` по префиксу
  (библиотека при этом пишет предупреждение «consider using send_login_sync» — это ожидаемо).
- **Счётчики** (airtime, пакеты) накопительные; на графиках показывается прирост за интервал,
  сброс счётчика (перезагрузка узла) даёт пропуск точки.
- **Mock**: при первом запуске на пустой БД генерируется синтетическая история за 48 ч.
- **Карта**: координаты — `adv_lat/adv_lon` контактов (0,0 = нет GPS). Линии: `out_path` контактов
  (мы → хопы → контакт), пути принятых сообщений каналов (отправитель по имени → хопы → мы),
  результаты trace, соседи своих репитеров. Хоп рисуется только при однозначном совпадении префикса.
- BLE не используется (по ТЗ). Административные команды репитеров (`send_cmd`, перезагрузка,
  настройки) в v1 не используются — только чтение.
